# Wozmon for the TRS-80 Color Computer 2

A port of Steve Wozniak's Apple I monitor to the 6809, running on a CoCo 2.

A *monitor* is the smallest useful thing a computer can run: it lets you look
at memory, change it, and execute code, with no operating system underneath.
The original was 256 bytes of ROM and was the entire software an Apple I
shipped with in 1976.

This port keeps the original's command set exactly, and talks to the CoCo's
hardware directly — it scans the keyboard matrix and writes to the video
chip itself, so it works even when BASIC has not initialised.

## Commands

```
1000            examine the byte at $1000
1000.100F       dump a range, 8 bytes per line
1000: DE AD     store bytes starting at $1000
:BE EF          keep storing where the last store left off
1000R           run the machine code at $1000

left-arrow      backspace
BREAK           cancel the line
```

There is deliberately **no way to exit**, exactly as on the Apple I. Press
RESET to leave.

Typing `1000: DE AD` echoes `1000: 00` first. That is not a bug: the monitor
reads the line left to right, so `1000` on its own is an *examine* request
and prints the current byte. Only then does `:` switch it into store mode.
The Apple I behaves identically.

## Two versions

| Source | Builds | Size | Cursor |
|---|---|---|---|
| `src/wozmon.asm` | `wozmon.bin`, `wozmon.rom` | 533 bytes | none |
| `src/wozmon-cursor.asm` | `wozmonc.bin`, `wozmonc.rom` | 571 bytes | blinking `@` |

They differ in exactly one routine, `GETKEY`.

Why two? **The original Wozmon contains no cursor code at all.** The Apple I
did show a blinking `@`, but it was generated by the terminal *hardware*,
with no help from the software. The CoCo's video chip has no hardware cursor
either, so reproducing what an Apple I user actually saw means writing new
code the original never had. The plain build stays faithful; the cursor build
gets the authentic look. Take your pick.

## Building

Needs [lwtools](http://www.lwtools.ca/) (`lwasm`).

```sh
make            # builds all four images into build/
make clean
```

## Running it on a CoCo

Both `.BIN` files load at `$4000` and need a **32K or 64K** machine.

### The ready-made disk

[`WOZMON.DSK`](WOZMON.DSK) is a standard 35-track single-sided Disk BASIC
image with both builds already on it. Mount it in an emulator, or write it
to a real disk or an SD/floppy emulator:

```
WOZMON .BIN     the plain monitor, faithful to the original
WOZMONC.BIN     the same monitor with a blinking @ cursor
```

```basic
CLEAR 200,&H3EFF
LOADM"WOZMON"
EXEC
```

Swap `WOZMONC` for the cursor version.

`CLEAR 200,&H3EFF` moves BASIC's memory ceiling below the monitor's
workspace. Without it, BASIC's string space sits on top of our variables and
corrupts them. Remember there is no way back out — RESET is the exit.

### Building the disk yourself

`make` writes the four images to `build/`; put the `.BIN` files on a disk
with whatever tooling you normally use.

The `.ROM` files are 8K cartridge images. **These are untested on hardware** —
see [Status](#status).

## Memory map

```
$0400-$05FF   text screen, 32x16
$3F00-$3FFF   workspace  (variables, and the 128-byte line buffer at $3F80)
$4000-$4214   monitor code
```

The cartridge build relocates to `$C000` with its workspace at `$0600`.

Variables live in one 256-byte page so they can be reached through the 6809's
`DP` register in two-byte instructions — the equivalent of the 6502's zero
page, and a large part of why the port stays small.

## Sample program: HAPPY SEPTANDY

Septandy is the CoCo and Tandy community's September celebration. This
prints it and returns to the monitor. Source with full line-by-line
commentary is in [`examples/septandy.asm`](examples/septandy.asm).

**Type this in:**

```
1000: 8E 10 0D A6 80 27 05 BD
1008: 40 3C 20 F7 39 0D 48 41
1010: 50 50 59 20 53 45 50 54
1018: 41 4E 44 59 00
1000R
```

**What you'll see** (each store line echoes the old byte first, as explained
above):

```
1000: 00
1008: 40 3C 20 F7 39 0D 48 41
1008: 00
1010: 50 50 59 20 53 45 50 54
1010: 00
1018: 41 4E 44 59 00
1018: 00
1000R
1000: 8E
HAPPY SEPTANDY
```

**The source:**

```asm
PUTCHAR     equ $403C           ; the monitor's own screen routine
CR          equ $0D

            org $1000

START       ldx   #MSG          ; X = address of the text
LOOP        lda   ,x+           ; fetch a character, advance X
            beq   DONE          ; zero byte marks the end
            jsr   PUTCHAR       ; print it
            bra   LOOP
DONE        rts                 ; back to the monitor prompt

MSG         fcb   CR
            fcc   "HAPPY SEPTANDY"
            fcb   0
```

Three things make this work, and they apply to anything you write:

- **It borrows the monitor's `PUTCHAR`** at `$403C` instead of writing to
  screen memory, so it inherits cursor tracking, ASCII translation and
  scrolling. That address is for the `.BIN` build at `$4000`; the cartridge
  build relocates it.
- **`RTS` returns you to the monitor.** `R` reaches your code via `JMP [XAM]`
  from inside a routine the main loop called with `JSR`, so that return
  address is still on the stack. End with `RTS` (`$39`) and you keep the
  monitor; fall off the end and you are reaching for RESET.
- **Uppercase only.** The video chip has a 64-character set with no lowercase.
  `PUTCHAR` masks with `AND #$3F`, so lowercase `e` (`$65`) would come out as
  `%`.

There is a second, simpler example in [`examples/hello.asm`](examples/hello.asm).

## Notes on porting 6502 to 6809

Both CPUs come from the same lineage and the translation is mostly pleasant —
several 6502 workarounds collapse into single 6809 instructions:

| Wozmon (6502) | This port (6809) |
|---|---|
| `LDA IN,Y` with 8-bit `Y` | `LDA B,U` — accumulator-offset indexing |
| `SETADR` two-byte copy loop | `LDX <HEX` / `STX <ST` / `STX <XAM` |
| `JMP (XAML)` | `JMP [XAM]` |

Two differences bite, and both caused real bugs here:

**The carry convention on compare is inverted.** The 6502 sets carry when
`A >= M`; the 6809 sets it on *borrow*, when `A < M`. The original folds that
carry into `ADC #$88` when parsing hex letters. On the 6809 the carry is not
there, so the `+1` has to be baked into the constant: **`ADDA #$89`**. With
`#$88`, `'A'` produces `$F9` instead of `$FA` and every hex digit A–F is
silently rejected.

**`D` is `A:B`, not a separate register.** Collapsing the 16-bit compare to
`LDD`/`CMPD` looks like an obvious win, but `B` holds the parser's position
in the typed line, so the compare quietly destroyed it. The 6502 original has
no such clash — its compare uses `A` alone with the index in `Y`. The port
uses `CMPX` instead.

The broader lesson: use the 6809's *semantic* branch mnemonics (`BLO`, `BHS`,
`BLS`) rather than transliterating `BCC`/`BCS`. Those read the same on both
chips and would have prevented the first bug entirely.

## Status

Working on real hardware. Verified on a CoCo 2:

- the video mapping (`AND #$3F`, no inverse-video bit)
- the keyboard matrix
- examine, dump, store and run

**Not yet verified:** the cartridge autostart signature — what Color BASIC's
reset routine checks at `$C000` before jumping there. Both `.ROM` images are
therefore unproven. The `.BIN` builds are known good.
